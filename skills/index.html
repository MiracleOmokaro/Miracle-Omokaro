Stored XSS in a notes application (lab)

A notes field stored unsanitized HTML and executed in another user’s session. Write-up names source, sink, and a fix that would survive a real code review.

Stored XSSSession impactOutput encoding

What I actually found

The application reflected a note’s body into a dashboard without context-aware encoding. A payload that closed the existing tag and opened a script ran in the victim’s browser when they opened the shared note. This is a lab, not a production bounty — the value is the method.

Method

Map every place user content is stored. For each, identify the sink (innerHTML, href, event handler, template). Test the encoding in that specific context, not a generic “does it strip script tags” check. Escalate only after a reliable execution path exists.

  • Source: note body, persisted in the application database
  • Sink: dashboard renderer inserting HTML
  • Impact in lab terms: account takeover via session cookie if HttpOnly is absent, or arbitrary actions in the victim origin

What I would tell a developer

Encode on output for the context you are rendering into. Treat Markdown or “rich text” as a parser problem with an allow-list, not a sanitize-later problem. Add a CSP that would have made this payload noisy even if encoding failed.

Horizontal IDOR on invoice objects (lab)

Invoice identifiers were sequential and authorization was missing on GET. Another user’s invoice returned in full. The interesting part is how often this pattern survives in SME software.

IDORAccess controlObject mapping

The bug class

The application trusted that anyone who knew (or could guess) an invoice id was allowed to read it. I mapped the object, incremented the id, and received another principal’s record. No fancy payload. This is the class I care about for Polymorph-generated SME apps: authorization on every object, every method.

How upcoming practitioners should hunt it

Do not start with scanners. Start with a second account. For every id you see — numeric, UUID, filename — ask: what happens if I swap it? Test GET, POST, PUT, DELETE, and the export/print endpoints people forget.

Fix

Authorization check bound to the session’s principal, not the presence of an id. Prefer non-sequential identifiers as defense in depth, never as the only control.

CORS misconfiguration with credentialed reads (lab)

The API reflected an attacker origin in Access-Control-Allow-Origin and allowed credentials. A simple cross-origin read would have exposed authenticated JSON.

CORSTrusted origin reflection

Why this is not “just CORS”

CORS is a browser rule. When a server reflects arbitrary origins and sets credentials true, it has volunteered to be read from an attacker page while the victim is logged in. The lab made that mechanical. Production SME APIs make it common.

Check

Send Origin: https://evil.example and read the response headers. If your origin comes back and Allow-Credentials is true, stop and write the report. Do not need a full chain to know the configuration is wrong.

Verbose error leakage on a debug path (lab)

A leftover debug endpoint returned stack traces and framework versions. Low severity alone; high value as a foothold for everything else.

Information disclosureAttack surface reduction

The lesson I actually wanted

Low findings teach hygiene. Stack traces, version banners, and debug routes are how a later high-severity bug becomes easy. Polymorph’s generator now treats debug routes as a ship-blocker, not a later ticket.
